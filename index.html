Portable AI: Running Llama Models
with Ollama from a USB Drive

A complete enterprise setup guide for offline-capable, data-sovereign LLM inference — no cloud, no installation, no data egress.

Tested OS: Windows 11 22H2+, macOS 14 Sonoma+, Ubuntu 22.04 LTS Ollama: v0.3.x+ (verify flags against latest docs) Audience: AI/Cloud Engineers · Presales · Security Architects

01 Executive Summary

This guide enables engineers, presales consultants, and architects to deploy a fully self-contained Llama/Ollama inference environment on a USB drive — bootable and functional on any compliant Windows, macOS, or Linux host without permanent installation or cloud connectivity. The primary value is data sovereignty: prompts, model weights, and outputs never leave the physical device, satisfying air-gapped, FSI, and government compliance requirements. The outcome is a portable, encrypted, enterprise-governed AI lab that accelerates customer PoCs, restricted-environment demonstrations, and secure experimentation — delivered in under 45 minutes per device.

🏛️ Air-gapped / government environments
🏦 FSI & critical infrastructure PoCs

🔒 Data-sovereign experimentation — prompts stay local
🧪 Rapid workshop & lab setup
🚀 Presales field engineering toolkit

🚫 ZERO NETWORK EGRESS — All data, prompts, and model weights remain on-device. No telemetry. No cloud calls.

Component Roles

💾 USB Drive

  • Stores Ollama binaries for all three OS platforms
  • Houses model weights in /models (OLLAMA_MODELS target)
  • Contains OS-specific launcher scripts with relative paths
  • Encrypted at rest (BitLocker To Go / VeraCrypt / LUKS)

🖥️ Host Machine

  • Provides RAM/VRAM for model inference (compute only)
  • Nothing installed permanently — zero host footprint
  • Ollama process runs from USB binary, exits cleanly on shutdown
  • GPU acceleration used automatically if CUDA/Metal available

⚙️ Ollama API Server

  • Exposes OpenAI-compatible REST API on localhost:11434
  • OLLAMA_MODELS env var redirects model storage to USB
  • Manages model loading, unloading, and quantization
  • Must be stopped cleanly before USB ejection

1
Format the USB Drive as exFAT
Goal: Ensure the filesystem supports files larger than 4 GB (required for model weights)

FAT32 has a hard 4 GB per-file limit. Llama model shards routinely exceed this. exFAT is natively supported on all three target OS platforms and has no practical per-file size limit.

WINDOWS — Disk Management or PowerShell
# Replace X: with your USB drive letter — confirm before running
format X: /FS:exFAT /Q /V:PortableAI
macOS — Terminal
# List disks to identify your USB disk identifier
diskutil list
# Replace diskN with your USB disk (e.g. disk2) — NOT your system disk
diskutil eraseDisk ExFAT PortableAI MBRFormat /dev/diskN
Linux — Terminal (requires exfatprogs)
sudo apt install exfatprogs   # Ubuntu/Debian
# Identify your USB device — lsblk or fdisk -l
sudo mkfs.exfat -n PortableAI /dev/sdX1  # sdX1 = USB partition
Screenshot 1
Terminal output showing successful exFAT format completion
Callouts: ① Drive letter / device path ② Filesystem type = exFAT ③ Volume label = PortableAI
❌
Common Error: "File too large" If you see this when moving model files, the drive was formatted as FAT32. Re-format as exFAT — there is no workaround for the 4 GB FAT32 limit.

Goal: Establish a portable, OS-agnostic directory layout on the USB root
WINDOWS — PowerShell (replace E: with your drive letter)
$usb = "E:"
New-Item -ItemType Directory -Force -Path "$usb\ollama\windows"
New-Item -ItemType Directory -Force -Path "$usb\ollama\linux"
New-Item -ItemType Directory -Force -Path "$usb\ollama\macos"
New-Item -ItemType Directory -Force -Path "$usb\models"
New-Item -ItemType Directory -Force -Path "$usb\scripts"

4
Configure OLLAMA_MODELS Environment Variable
Goal: Redirect model storage from the host's home directory to the USB /models folder

By default, Ollama stores models in ~/.ollama/models (host profile). This must be overridden to ensure models land on the USB. This is handled by the launcher scripts in Step 5 — do not set this permanently in system environment variables or models will bind to that host.

WINDOWS — Set per-session (handled in launcher script)
set OLLAMA_MODELS=E:\models
# This is injected dynamically by start-ollama.bat using %~dp0 — see Step 5
macOS / Linux — Set per-session
export OLLAMA_MODELS=/Volumes/PortableAI/models
# Dynamically resolved in start-ollama.sh using $SCRIPT_DIR — see Step 5
⚠️
Do Not Persist This Variable System-Wide Setting OLLAMA_MODELS permanently in system environment variables will break Ollama when the USB is not connected. Always set it session-scoped within the launcher scripts.

5
Create Portable Launcher Scripts
Goal: Scripts that resolve paths relatively so the USB works regardless of drive letter or mount point

Drive letters change on Windows and mount points differ on Linux/macOS. Use %~dp0 (Windows) and $(dirname "$0") (Unix) to resolve paths relative to the script's own location.

/scripts/start-ollama.bat
@echo off
:: Portable Ollama Launcher for Windows
:: %~dp0 resolves to the script's directory with trailing backslash
setlocal

:: Resolve USB root (one level up from \scripts\)
set USB_ROOT=%~dp0..

:: Point model storage at USB
set OLLAMA_MODELS=%USB_ROOT%\models

:: Optional: bind only to localhost (default, but explicit for security)
set OLLAMA_HOST=127.0.0.1:11434

:: Launch Ollama server from USB binary
echo [PortableAI] Starting Ollama server...
echo [PortableAI] USB Root : %USB_ROOT%
echo [PortableAI] Models   : %OLLAMA_MODELS%
echo [PortableAI] API      : %OLLAMA_HOST%
echo.

"%USB_ROOT%\ollama\windows\ollama.exe" serve

endlocal
pause
/scripts/start-ollama.sh
#!/usr/bin/env bash
# Portable Ollama Launcher for macOS and Linux
set -euo pipefail

# Resolve USB root (one level up from /scripts/)
SCRIPT_DIR=$( cd -- "$( dirname -- "${BASH_SOURCE[0]}" )" &>/dev/null && pwd )
USB_ROOT="$(dirname "$SCRIPT_DIR")"

# Detect OS and select binary
case "$(uname -s)" in
  Darwin*)  OLLAMA_BIN="$USB_ROOT/ollama/macos/ollama" ;;
  Linux*)   OLLAMA_BIN="$USB_ROOT/ollama/linux/ollama" ;;
  *)        echo "Unsupported OS"; exit 1 ;;
esac

# Set model storage to USB
export OLLAMA_MODELS="$USB_ROOT/models"
export OLLAMA_HOST="127.0.0.1:11434"

# Make binary executable if needed
chmod +x "$OLLAMA_BIN"

echo "[PortableAI] Starting Ollama server..."
echo "[PortableAI] USB Root : $USB_ROOT"
echo "[PortableAI] Models   : $OLLAMA_MODELS"
echo "[PortableAI] Binary   : $OLLAMA_BIN"
echo "[PortableAI] API      : $OLLAMA_HOST"
echo ""

"$OLLAMA_BIN" serve

Pull Models to the USB Drive
Goal: Download model weights directly to /models on the USB — not to the host profile

Run this from the same terminal session where OLLAMA_MODELS is set. Models download to the active OLLAMA_MODELS path. Confirm before pulling.

ALL PLATFORMS — Verify path, then pull
# Confirm OLLAMA_MODELS is set to USB path
echo $OLLAMA_MODELS   # Unix: should show USB path
# echo %OLLAMA_MODELS%   # Windows

# Pull a 3B model (suitable for 8 GB RAM hosts, ~2 GB download)
ollama pull llama3.2:3b

# Pull 8B model for capable hosts
ollama pull llama3.1:8b

# Confirm model landed on USB — not host profile
ls -lh /Volumes/PortableAI/models/manifests/   # Unix
# dir E:\models\manifests\   # Windows

Safe Shutdown and USB Ejection
Goal: Stop the Ollama server cleanly before ejecting to prevent model file corruption

Never physically remove the USB while the Ollama server is writing to model files. Model corruption from hot-eject requires a full re-pull to recover.

ALL PLATFORMS — Stop server, then eject
# Stop Ollama server (Ctrl+C in the launcher terminal, or:
pkill ollama          # macOS / Linux
taskkill /F /IM ollama.exe   # Windows

# Confirm no processes hold the USB (Linux)
lsof /media/$USER/PortableAI | grep -v "^COMMAND"

# Safe eject
diskutil unmount /Volumes/PortableAI    # macOS
# Use system tray "Safely Remove Hardware" on Windows
# udisksctl unmount -b /dev/sdX1        # Linux
Screenshot 10
Terminal showing ollama process terminated and successful USB unmount confirmation
Callouts: ① Process termination confirmation ② lsof output showing no open handles ③ "Volume unmounted" success message

05 Performance Optimization

⚡ USB Bus Speed Impact

  • Model loading is I/O bound — USB speed is critical here
  • Inference (token generation) runs from host RAM/VRAM — USB speed irrelevant once loaded
  • USB 3.2 Gen 2 (10 Gbps): ~1–3 min load for 8B model
  • USB 3.0 (5 Gbps): ~3–6 min load for 8B model
  • NVMe SSD enclosure via USB4/Thunderbolt: near-native load speeds

🗜️ Quantization Trade-offs

  • Q4_K_M: ~50% size reduction, minimal quality loss — recommended default
  • Q8_0: ~25% size reduction, near-full quality — use when accuracy critical
  • Q2_K: aggressive compression — noticeable quality degradation
  • Use :q4_K_M tag suffix when pulling (e.g. llama3.1:8b-q4_K_M)

🎮 GPU Acceleration

  • NVIDIA: CUDA auto-detected by Ollama if drivers installed on host
  • Apple Silicon: Metal automatically used — best portable GPU performance
  • AMD: ROCm support on Linux (verify against current Ollama docs)
  • GPU inference is 5–20x faster than CPU for 7B+ models
  • Weights load from USB to VRAM — same I/O bottleneck on first load

06 Security & Governance Controls

🏛️
Enterprise Mandatory Section All controls below are required before issuing USB AI devices in regulated or enterprise environments. Non-compliance may breach endpoint security policy, data classification requirements, or AI governance frameworks.

🔒 Drive Encryption

  • Windows: BitLocker To Go (AES-256, PIN or passphrase)
  • Cross-platform: VeraCrypt hidden volume (XTS-AES-256)
  • Linux: LUKS2 with Argon2id KDF
  • Encrypt before placing any binaries or models on the drive
  • Store recovery keys in enterprise key management (HSM/KV)

📋 Model Provenance

  • Pull only from ollama.com/library (official registry)
  • Record SHA256 of each model manifest in /docs/checksums.txt
  • Do not pull from community registries without security review
  • Implement model inventory as part of AI asset register
  • Apply model risk classification (public, internal, restricted)

🌐 API Binding Controls

  • Always set OLLAMA_HOST=127.0.0.1:11434 — never 0.0.0.0
  • Setting to 0.0.0.0 exposes inference to all network interfaces
  • Confirm binding with netstat -an | grep 11434
  • No authentication on Ollama API by default — localhost-only is the control

🖥️ Endpoint Policy

  • USB control policies (e.g., Intune, Defender for Endpoint) may block execution
  • Pre-approve USB device IDs in endpoint management before deployment
  • EDR may alert on unsigned binaries — whitelist binary hash with SOC
  • DLP: confirm no prompt data is captured by endpoint DLP agents
  • Conduct a binary signing review with your security team

07 Troubleshooting

SymptomRoot CauseFix
Error: listen tcp 127.0.0.1:11434: bind: address already in use Host Ollama installation already running on port 11434 Stop host: ollama stop or taskkill /F /IM ollama.exe. Or change USB launcher to use port 11435 via OLLAMA_HOST=127.0.0.1:11435
Models downloading to ~/.ollama/models instead of USB OLLAMA_MODELS not set in the current shell session Run echo $OLLAMA_MODELS to verify. Re-source the launcher script: source ./start-ollama.sh or restart from the launcher terminal
The file is too large for the destination file system USB formatted as FAT32 (4 GB file size limit) Re-format as exFAT. No workaround exists for FAT32 with large model files. See Step 1.
Model load takes 10+ minutes; very slow token generation USB operating at USB 2.0 speeds or drive seated in USB 2.0 port Use a USB 3.x port (blue connector on most hosts). Confirm bus speed: system_profiler SPUSBDataType | grep Speed (macOS)
macOS cannot open "ollama" because Apple cannot check it for malicious software macOS Gatekeeper blocking unsigned binary Run: sudo xattr -rd com.apple.quarantine /path/to/ollama. Or: System Settings → Privacy & Security → Allow. Verify binary hash first.
Linux: Permission denied when running ollama script USB mounted with noexec flag, or file permissions stripped Copy binary to /tmp: cp $USB/ollama/linux/ollama /tmp/ollama && chmod +x /tmp/ollama. Set OLLAMA_MODELS to USB path and run from /tmp.
Error: model requires more system memory than is available Host RAM insufficient for selected model (e.g., 8B model on 8 GB host) Switch to a smaller model: ollama run llama3.2:3b. Close other applications. Check RAM: free -h (Linux) / Task Manager (Windows)
Antivirus quarantines ollama.exe or ollama binary Heuristic detection of unsigned or unknown binary Submit binary hash to AV vendor for whitelisting. Verify SHA256 against GitHub release checksums first. Pre-approve with Security Ops before deployment.
ollama: command not found after launching System PATH does not include USB binary directory Use full path: ./ollama run llama3.2:3b or $USB_ROOT/ollama/linux/ollama run. The launcher scripts handle this automatically — use them.
